## 背景

現況是純型錄站：客人看完商品後，要自己打電話或用 LINE 說明想要什麼。問題出在**傳達**——
口頭講品項規格容易漏、容易錯，老闆也沒有一份可以照著處理的清單。

現行成交流程是：客人匯款到公司戶頭 → 老闆確認入帳 → 出貨。
這個流程本身沒問題，**但客人匯款後完全無法追蹤進度**——不知道老闆收到款沒、何時出貨。
這是目前體驗上最大的缺口，也是本系統要解決的第二個問題。

同時有一個既有事實會決定整個設計：**網站上的價格經常來不及更新**。
所以價格在本系統中的定位是「**參考價**」，不是承諾價；**老闆確認後的金額才算數**。

## 目標

1. 讓客人把「我要哪些東西、各要幾個」結構化地送出來，老闆有一份清楚的清單可以照著處理。
2. 讓客人**全程看得到訂單狀態**：待確認 → 待付款 → 已付款 → 已出貨。

**不做**：線上刷卡（第一版維持匯款，見「收款」章節）、即時庫存扣減、串接物流 API。
訂購單送出 ≠ 交易成立，老闆確認金額後才進入付款。

## 關鍵設計決定

### 1. 不經過 LINE 送單

原本考慮過「購物車 → 組成訊息 → 開 LINE 預填送出」。**不採用**。

LINE 官方帳號當初只是為了「讓客人有地方留言」而放的，訂購單本身已經取代這個用途。
訂單直接寫進 Directus，老闆從後台處理，比在 LINE 對話裡往上翻訊息可靠得多。

拿掉這一步同時消除四個問題：網址長度上限、使用者可能不按送出、孤兒單、單號得人工唸。
LINE 按鈕維持現狀，繼續當「聯絡我們」的入口。

### 2. 價格是參考價，且要能看出「客人看到的價 vs 現在的價」

因為價格常來不及改，系統必須誠實：

- 前台送出頁明確標示「**價格與庫存以專人確認為準**」。
- `order_items` 存下**下單當時的單價快照**，同時保留 `variant` 關聯指向現行資料。
- 老闆在後台看訂單時，兩個數字並列——一眼就知道客人看到的是不是舊價，
  可以在電話裡直接解釋，而不是被問到才發現。

這是快照欄位在本專案的真正價值，跟一般電商「保護歷史金額」的動機不同。

### 3. 強制登入才能送出

已確認採用。理由：

- `customers` 已有公司名、統編、電話、送貨地址，可自動帶入，客人不用重打。
- 避免開放匿名寫入（目前 Directus public role **完全沒有任何 create 權限**，
  開第一個匿名寫入會連帶要處理灌單、個資讀取範圍等問題）。
- 老闆拿到的訂單一定對應得到一個真實客戶，不會有查無此人的單。

B2B 五金客戶多為回頭客，登入的摩擦遠低於上述成本。

### 4. 老闆的操作介面 = Directus admin UI

**不自建後台。** `views/Admin.vue` 目前只有殼，做完整 CRUD 曠日費時且沒有必要。
Directus admin UI 設定妥當就足夠好用（詳見「後台設定」章節）。

## 資料模型

### `orders`（訂購單）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | integer, auto-increment, PK | 內部主鍵 |
| `order_number` | string, unique | 對外單號，格式 `GTS-260901-0042`，由 Flow 產生 |
| `status` | string (dropdown) | 見下方狀態機 |
| `customer` | M2O → `customers` | 下單者，必填 |
| `contact_name` | string | 本單聯絡人，預設帶入 `customers.user_name`，可改 |
| `contact_phone` | string | 本單聯絡電話，預設帶入 `customers.phone`，可改 |
| `contact_address` | string | 本單送貨地址，預設帶入 `customers.shipping_address`，可改 |
| `note` | text | 客人備註（取代原本 LINE 留言的角色） |
| `subtotal` | integer, nullable | **客人送出時**的參考小計；僅計有價品項，前端不可寫 |
| `has_quote_items` | boolean | 是否含待報價品項；由後端計算 |
| `shipping_fee` | integer, **nullable、無預設** | 運費。`null` ＝ 套滿額免運規則；填入任何數字（含 0）＝ 手動指定，Flow 不覆蓋 |
| `discount` | integer, default 0 | 折扣，老闆填 |
| `confirmed_total` | integer, nullable | **老闆確認後的應付金額**，由 Flow 自動加總（唯讀） |
| `payment_note` | string, nullable | 客人回報的匯款帳號末五碼 |
| `paid_at` | timestamp, nullable | 老闆確認入帳的時間 |
| `shipping_method` | string (dropdown) | 宅配 / 自取 / 超商 |
| `tracking_number` | string, nullable | 貨運單號，老闆填 |
| `shipped_at` | timestamp, nullable | 出貨時間 |
| `items` | O2M → `order_items` | 品項明細 |
| `date_created` / `user_created` | Directus 內建 | |

**為什麼聯絡資訊要獨立欄位而非只靠 `customer` 關聯**：五金行客人常常「這批送工地、那批送公司」。
讓他每張單能填不同的聯絡方式與地址，比強制沿用會員資料實用。預設帶入、允許修改。

### `order_items`（訂購單品項）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | integer, auto-increment, PK | |
| `order` | M2O → `orders` | |
| `variant` | M2O → `product_variants`, nullable | 軟參照，用來連回商品與比對現價 |
| `product_name` | string | 快照 |
| `spec_name` | string | 快照 |
| `sku` | string | 快照 |
| `unit_price` | integer, nullable | **快照單價**（客人送出時看到的）；`null` 代表當時為「詢價」 |
| `confirmed_price` | integer, nullable | **老闆確認的單價**；留空代表沿用 `unit_price` |
| `quantity` | integer | |

`variant` 可為 null 是刻意的——商品日後被刪除時，訂單仍須完整可讀。
顯示一律以快照欄位為準，`variant` 只用於「連回商品頁」與「比對現價」。

### 狀態機

| 狀態 | 意義 |
|---|---|
| `pending` 待確認 | 客人剛送出，老闆還沒看 |
| `quoted` 待付款 | 老闆已確認金額與庫存，客人看到應付金額與匯款資訊 |
| `paid` 已付款 | 老闆對帳確認入帳 |
| `shipped` 已出貨 | 已填貨運單號，客人可自行查件。**這是正常終態** |
| `cancelled` 已取消 | 客人取消或無法供貨 |

**刻意不設「已完成」**：出貨即結案，沒有收貨確認機制，多一個狀態只是多一次操作。
要區分「待辦 vs 結案」用後台書籤 filter 掉 `shipped` 即可。

### 老闆實際要按幾次？三次，而且每次是一個按鈕

用 **Directus 手動觸發 Flow**（在訂單頁面顯示按鈕），不是讓老闆手動改下拉選單：

| 時機 | 按鈕 | Flow 自動執行 |
|---|---|---|
| 確認金額與庫存後 | **確認報價** | 算 `confirmed_total`、套用運費規則、`status → quoted`、寄信通知客人 |
| 對帳確認入帳 | **確認收款** | 設 `paid_at`、`status → paid`、寄信通知 |
| 出貨、填完 `tracking_number` | **確認出貨** | 設 `shipped_at`、`status → shipped`、寄信通知 |

> 關鍵認知：**這三個動作老闆現在本來就在做**（確認金額、對帳、出貨），
> 只是做完沒留下紀錄、客人也看不到。系統增加的成本僅是「按一個按鈕」，
> 換得客人自助查進度、老闆免於一一回覆。每個按鈕都順帶寄信通知，實際上是淨省時間。

### 老闆怎麼改金額

原則：**客人送出的是參考金額，老闆確認的才算數。**

老闆只需要動三種欄位——`order_items.confirmed_price`（單價）、`orders.shipping_fee`（運費）、
`orders.discount`（折扣）。`confirmed_total` 由 Flow 自動加總並設為**唯讀**，避免人工加總算錯：

```
confirmed_total = Σ (confirmed_price ?? unit_price) × quantity + shipping_fee − discount
```

前台「我的訂購單」把 `subtotal`（送出時參考）與 `confirmed_total`（確認後應付）**並列顯示**，
價格有調整也是透明的，不會產生爭議。

### 運費：滿額免運，自動帶入

老闆希望做滿額免運，因此**不逐單填運費**。`site_settings` 新增兩個欄位：

| 欄位 | 說明 |
|---|---|
| `free_shipping_threshold` | 滿額免運門檻 |
| `default_shipping_fee` | 未達門檻時的預設運費 |

「確認報價」Flow 自動判斷：

```
商品小計 = Σ (confirmed_price ?? unit_price) × quantity − discount
shipping_fee = 商品小計 >= free_shipping_threshold ? 0 : default_shipping_fee
```

⚠️ 門檻**必須用「商品小計」（不含運費）判斷**，不能用 `confirmed_total`，否則變成循環計算。

`shipping_fee` 仍允許老闆手動覆寫，處理大件、離島等例外——即「九成自動算好，例外才手動改」。

> 實作上以 **`shipping_fee` 是否為 `null`** 來分辨「尚未設定」與「老闆刻意指定」。
> 因此該欄位不可有 default 0，否則兩種情況無法區分（見文末「與原提案的差異」）。

### 收款：第一版維持匯款，不串金流

沿用現行作法——客人匯款到公司戶頭、老闆確認入帳後出貨。**這是刻意的決定，不是偷懶**：

- **成本**：匯款 0% 手續費；串金流要付約 2.8%（PAYUNi 國內卡公告費率）。
  以五金的毛利，這個差距不是小數字。
- 匯款唯一的缺點是**人工對帳**，在訂單量還小的時候，這個成本遠低於 2.8%。

系統要做的只是把流程講清楚：狀態進入 `quoted` 時，前台顯示匯款資訊
（銀行、帳號、**應付金額、請於備註填單號**）；客人匯完可按「我已匯款」並填帳號末五碼
（寫入 `payment_note`），老闆對帳時就知道對應哪一筆。

**匯款資訊存在 `site_settings`**（銀行名稱、帳號、戶名三個欄位），老闆可自行修改，不寫死在程式。

> **只在「待付款」狀態的訂單明細顯示，不放在任何公開頁面。**
> 公司帳號本身不算機密（發票、報價單上都有），但沒必要讓爬蟲與路人取得。
> 之所以放進系統而非「老闆再私下給」，是為了流程速度——客人一被報價就能立刻付款，
> 不必等下一次人工聯絡。

> 未來若訂單量成長到人工對帳吃力，再加上綠界／藍新的「收款連結」作為第二個付款選項即可，
> **不需要重做系統**，也不需要自建後端或串完整金流 API。

#### 對帳作業規則（2026-09-10 確立）

前提釐清：**`payment_note` 不是付款的證據，是對帳的比對線索。** 錢有沒有到帳，唯一的
真相來源是銀行明細——客人可能填錯、沒填、或用別的戶頭匯款。所以系統從一開始就沒有讓
客人的回報去推進狀態（`customer access` 的 update 只開放 `payment_note`，且限
`status = quoted`；`paid` 一律由老闆按下確認）。

**驅動老闆去對帳的是銀行通知，不是客人的回報。**「客人回報」這個事件只在客人配合時才
發生，不能當驅動器——否則沒填的單永遠不會有人去看。所以也**刻意不做「客人回報後寄信
給老闆」那封信**：銀行已經會通知，那封信不增加資訊，只在客人配合時才發。

（「新單成立」那封信不同——客人送單沒有任何外部觸發器會通知老闆，所以那封是必要的，
已在 `訂購單送出後處理` flow 實作。）

老闆拿到一筆入帳後的三種情況：

| `payment_note` | 處理 |
|---|---|
| **空的** | **不要填。** 空著代表「客人沒照流程走，我們自己對出來的」，那是有意義的資訊；填了反而讓這個欄位變成「某個人打的字」，之後沒人能判斷值是誰寫的 |
| **有值且與銀行相符** | 什麼都不用做，直接確認收款 |
| **有值但與銀行不符** | 打電話確認（多半是打錯字，或用配偶／公司戶匯款），**然後修正成銀行上的數字** |

第三種要修正而不是留著，理由是「留著一個錯的聲明」比「修正它」更誤導：老闆下次打開這張
單，會看到一個與銀行不符的數字，又要重新判斷一次是不是配對錯了。原值不會消失——Directus
的 revisions 保留每次變更的完整快照，「客人原本填 54321、老闆改成 12345」查得回來。

> **`payment_note` 原本是 `readonly: true`，2026-09-10 關掉。**
>
> 權限上 `店務` 對 `orders` 是 `fields=['*']`，但欄位的 `meta.readonly` 是 UI 層設定、
> 對所有人生效（連 admin 也繞不過），所以在那之前**沒有人改得動它**——上面的規則 3
> 根本無法執行。這個唯讀當初應該是為了保護「客人的原話不被員工污染」。
>
> 關掉的理由：provenance 由 revisions 吸收（改動查得回來），而保留唯讀的代價落在
> **每一次對帳**（不符的值永遠留著，每次打開都要重新判斷），關掉的代價只落在
> 「有人惡意改」——而 `店務` 目前只有老闆一個使用者。
>
> ⚠️ 這不影響客人端：`customer access` 的 `app_access = false`（進不了後台），
> 他們寫這個欄位走前台 API、受 permission 管（`fields=['payment_note']` +
> `status = quoted`），與 UI 的 readonly 無關。
>
> 對照：`orders` 其餘九個唯讀欄位（`order_number`、`subtotal`、`confirmed_total`、
> `paid_at`、`shipped_at`…）都是「Flow 會覆蓋你所以不准手改」，`payment_note` 不屬於
> 那一類——沒有任何 Flow 會動它。它混在唯讀清單裡本來就是不一致的。

**沒有必要為此新增「內部備註」欄位。** 事後查帳的依據是：銀行明細（金額、日期、匯款人）
＋ `confirmed_total` ＋ `paid_at`（狀態改成已付款時自動填）＋ revisions（誰改的、何時改的）。
這四者都不依賴 `payment_note` 正確。

> **這整套人工比對會在串接金流後被淘汰**——金流會給權威的付款成功回調與交易序號。
> 所以現在不值得為它增加任何機制，上面三條規則是「不寫程式」就能執行的作業約定。

### 混單的總價語意

一張單可同時包含有價與詢價品項。因此：

- `subtotal` **只加總有價品項**。
- `has_quote_items` 為 true 時，前後台一律顯示為
  「小計 $X，另有 N 項待報價」，**不得**把它呈現成最終總價。

## 權限設計（Directus policies）

線上已有的 policy 結構（實測 2026-09-01）：

| Policy | app_access | 現況 |
|---|---|---|
| `$t:public_label`（未登入） | – | 型錄唯讀，**無任何 create 權限** |
| `customer access` | false | 型錄唯讀 + `customers` read/update；只用前台，不進 Directus |
| `店務` | true | `products` / `product_variants` / 圖檔 CRUD；老闆維護型錄用 |
| `Administrator` | true | 全開 |

新權限**掛在既有 policy 上，不新建**。

### 加到 `customer access`（客人送單）

| Collection | 動作 | 設定 |
|---|---|---|
| `orders` | create | Field Permissions 僅允許寫入 `customer, contact_name, contact_phone, contact_address, note, items`；Preset 強制 `status = pending` |
| `orders` | read | filter：`customer.user_id = $CURRENT_USER` |
| `order_items` | create | 隨 `orders` 的 nested create 一併建立 |
| `order_items` | read | filter：`order.customer.user_id = $CURRENT_USER` |

再加一條**極窄的 update**，用於「我已匯款」：

| Collection | 動作 | 設定 |
|---|---|---|
| `orders` | update | Field Permissions **只允許 `payment_note`**；filter：`customer.user_id = $CURRENT_USER` **且** `status = quoted` |

- 除上述之外**不開放 update / delete**。要改品項就打電話——符合實際作業，也省掉一整類邊界情況。
- `order_number`、`subtotal`、`confirmed_total`、`confirmed_price`、`shipping_fee`、
  `discount`、`status`、`paid_at`、`tracking_number` 前端一律不可寫。
- 特別注意：**`status` 絕不可讓客人寫**，否則客人可以自己把單改成「已付款」。
- public role 維持現狀。

### 加到 `店務`（老闆處理單）

| Collection | 動作 | 說明 |
|---|---|---|

## Flow（送出後的後端處理）

Trigger：`items.create` on `orders`（action，非阻斷）

1. **產生 `order_number`**：`GTS-` + `date_created` 的 `YYMMDD` + `-` + `id` 補零四位。
   直接由自增 `id` 推導，沒有併發搶號問題。
2. **重算 `subtotal` 與 `has_quote_items`**：讀回 `order_items`，

4. **重算 `confirmed_total`**：任何 `confirmed_price` / `shipping_fee` / `discount` 變動時重算。
5. **填 `tracking_number` 時**自動設 `shipped_at` 並把 `status` 推進 `shipped`。

## ~~⚠️ 待處理~~ ✅ 已解決：`orders.create` 的擁有權驗證失效

> **本節保留為問題紀錄，解法見文末「擁有權把關的最終作法」。**

階段 1 為了防止「客人把訂單掛到別人的 customer 上」，在 `customer access` 的
`orders.create` 權限設了 validation：

```json
{ "customer": { "user_id": { "_eq": "$CURRENT_USER" } } }
```

**這條規則不會生效。** Directus 的 create validation 只比對送出的 payload 本身，
**不做關聯查詢**——官方 repo 至今仍有一則開放中的功能請求就是要加上這個能力
（discussion #23968），另有回報指出這樣寫會拋 `Invalid undefined schema`。
也就是說它不只無效，**還可能讓建單直接失敗**。

### 影響

| | |
|---|---|
| 嚴重性 | 中。**不是資料外洩**——`orders.read` 的過濾條件是一般 permission filter，關聯路徑正常運作，客人仍然只讀得到自己的單 |
| 實際風險 | 已登入的客人若自行組 API 請求，可以把訂單建立在別人的 `customer` 底下，污染對方的訂單列表，老闆也會看到歸錯人的單 |
| 觸發門檻 | 需要登入且刻意繞過前端 |

### 建議修法：由伺服器端覆寫 `customer`

不要依賴 validation，改用**阻斷式（filter）flow** 在寫入前覆寫 `customer`：

1. 移除那條無效的 validation。
2. 新增 filter flow：trigger `items.create` on `orders`，
   讀 `customers` where `user_id = {{$accountability.user}}`，
   把 `customer` 覆寫成查到的 id 後回傳 payload。
3. **`customer` 仍保留在可寫欄位清單中**——這樣不論 Directus 內部是先做欄位權限檢查
   還是先跑 filter hook，都不會因為欄位不在白名單而被擋；客戶端送什麼都會被覆寫掉。
4. 查不到對應 customer 時**維持 payload 原樣、不要拋錯**，
   否則老闆或管理員在後台手動建單會被擋下（他們沒有 `customers` 資料列）。

### 尚未驗證的項目

以下需要**真實客戶帳號登入**才能測（開發者無法代為登入）：

- 客人能否成功送出訂購單（nested create 是否通過欄位權限）
- 客人只讀得到自己的訂購單
- 「我已匯款」只能寫入 `payment_note`、且限 `status = quoted`
- 上述 filter flow 生效後，偽造的 `customer` 是否確實被覆寫

### 階段 3 實測（2026-09-04，本機 dev + 真實登入）

**端到端跑通**：送出訂購單 → 單號 `GTS-260904-0006` 由 flow 產生、輪詢取得 →
訂單列表與明細 → 老闆按「確認報價」（480 + 運費 120 = 600）→
明細顯示應付金額與匯款資訊 → 客人回報末五碼。會員資料（姓名／電話／地址）正確帶入表單。

#### 修掉的兩個 bug

**1. 受保護頁面直接輸入網址會被導到 `/account`（既有 bug，被新路由暴露）**

`main.js` 的 `app.use(router)` 會**立刻**觸發首次導航，而 `authStore.init()` 在那之後才 await，
所以守衛看到的 `isAuthenticated` 一律是 `false` → 踢到 `/login` →
`AdminLogin.vue` 此時 init 已完成、看到已登入 → `replace` 到 `/account`。

`/account` 之所以看起來正常，是因為繞一圈剛好回到同一頁；在只有 `/account`
一個非管理員保護路由時不會被發現。守衛已改為先 `await authStore.init()`（冪等）。

**2. 老闆手動改狀態時，客人會看到「應付金額 NT$0」**

`confirmed_total` 仍是 `null`，明細頁原本會算成 NT$0——客人會以為不用付錢。
已改為顯示「金額尚在確認中」並隱藏「我已匯款」表單。

## 以真實客戶帳號驗證（2026-09-04）

改用 `customer` 角色的帳號（鯊鯊）實測，一次挖出兩個「用管理員測絕對測不到」的問題。
**管理員會繞過所有 policy，任何權限相關的驗證都必須用非管理員帳號進行。**

### 問題 1：那條 validation 讓所有客戶都送不出訂購單

`{"customer": {"user_id": {"_eq": "$CURRENT_USER"}}}` 不只擋偽造——
它對**合法建單也一樣回 400**：

```
Validation failed for field "customer". Value is required.
```

因為 Directus 只拿 payload 比對，`payload.customer` 是 UUID 字串，取不到 `.user_id`，
於是被判定成「值不存在」。功能等於完全不能用，只是先前用管理員測所以沒發現。**已移除。**

### 問題 2：flow 裡的 `item-read` 在客戶觸發時取不到資料

「訂購單送出後處理」對管理員建的單正常，對客戶建的單**單號與小計都是 null**。
逐項排除後確認：問題出在 `item-read` 這個 operation——
即使把 flow 的 `accountability` 設為 `null`、operation 的 `permissions` 設為 `$full`，
客戶觸發時它依然回空。

**解法：不要在 flow 裡回讀資料。** 改為直接從 `$trigger.payload.items` 計算，
整個 `item-read` 步驟拿掉。改完後客戶建單即正常產生單號與小計。

> 這個限制也讓「用 filter flow 反查 customers 再覆寫 `customer`」的原定解法行不通——
> filter flow 確實會執行（故意拋錯會讓建單回 500），但 `item-read` 一樣讀不到，
> 於是 payload 原樣通過、偽造仍然成立。該 flow 已刪除。

### 擁有權把關的最終作法：收進讀取條件

放棄在寫入時攔截，改為讓偽造出來的單**對任何人都不可見**。
`customer access` 的讀取條件同時要求兩件事：

```json
{ "_and": [
  { "customer":     { "user_id": { "_eq": "$CURRENT_USER" } } },
  { "user_created": {            "_eq": "$CURRENT_USER"   } }
]}
```

`user_created` 由 Directus 自動填入，客戶端無法偽造。因此：

| | `customer.user_id` | `user_created` | 結果 |
|---|---|---|---|
| 合法單 | ✓ 本人 | ✓ 本人 | 本人看得到 |
| 偽造單（掛在受害者名下） | 受害者 | 偽造者 | **兩人都看不到** |

`order_items.read` 與「我已匯款」的 update 條件同步收緊。

**殘留風險**：偽造單仍會寫進資料庫，老闆在後台會看到一張歸屬錯誤的單。
為此已把 `orders.user_created` 在後台顯示為「**送出者帳號**」並加註說明——
與「下單客戶」不一致即為異常。實測的偽造單長這樣：`customer=楊佳豪`／`送出者=鯊`，一眼可辨。

### 驗證結果（全部通過）

| 項目 | 結果 |
|---|---|
| 合法建單 | ✓ 200，`customer` 為本人，單號與小計正確產生 |
| 訂單列表只含自己的單 | ✓ 看不到他人訂單 |
| 直接讀他人訂單 | ✓ 403 |
| 偽造 `customer` 建單 | ✓ 建立後對任何人都不可見 |
| 客戶端寫入 `status` | ✓ 403（欄位權限） |
| 客戶端寫入 `confirmed_total` | ✓ 403（欄位權限） |
| 非 `quoted` 狀態回報匯款 | ✓ 403 |
| 客戶刪除自己的訂單 | ✓ 403（未開放 delete） |

測試訂單全數刪除，僅保留既有的 #5。

## 偽造訂單：從源頭擋掉（2026-09-04 最終作法）

前一節的「讀取條件把關」只是讓偽造單不可見，垃圾資料仍會寫進資料庫、需要人工清理。
改為**在寫入端擋下**。

### 作法

1. **`customer` 從 `customer access` 的可寫欄位清單移除**。客戶端送了就 403，
   資料庫不會產生任何東西。
2. `orders.customer` 改為可空；客戶送單時**完全不送**這個欄位。
3. 由「訂購單送出後處理」的 action flow 依 `{{$accountability.user}}` 反查
   `customers` 後補上，與 `order_number`、`subtotal` 一併寫入。
4. 讀取條件回歸單純的 `customer.user_id = $CURRENT_USER`——
   先前為擋偽造而加的 `user_created` 條件會讓**老闆代客人建的單，客人自己看不到**，
   偽造既已在寫入端擋住就不需要它了。

### 沿路排除掉的兩條死路

| 嘗試 | 結果 |
|---|---|
| filter flow 覆寫 `customer` | **回傳值不會成為實際 payload**。連「無條件覆寫成固定值」都無效。flow 本身確實會執行（故意拋錯會讓建單回 500），但改寫機制不生效。 |
| flow 內的 `item-read` | 客戶觸發時**一律回空**，即使 flow `accountability` 設 `null`、operation `permissions` 設 `$full`、甚至把 filter 條件寫死也一樣。 |

> 第二點同時是「送出後處理」flow 對客戶失效（單號與小計為 null）的原因。
> 該 flow 已改為直接從 `$trigger.payload.items` 計算，不再回讀 `order_items`。
> **但在 action flow 裡讀 `customers` 是可行的**——與 filter flow 的行為不同。

### 連帶的前端調整

`customer` 是建立**之後**才補上的，因此 POST 當下讀取條件不成立，
客戶讀不回自己的單：Directus 回 204、SDK 回 `null`，拿不到 id。
送出流程因此改為「記錄送出前自己看得到的最大 id → 輪詢等新訂單出現」。

## ⚠️ 兩個只有真實客戶帳號才會現形的問題

### 迴歸：登入客戶連商品頁都打不開

`customer access` 對 `products` / `site_settings` 的讀取權限用的是**明列欄位清單**，
而階段 0 新增的 `iopen_url`、`shopee_url` 不在其中——整個商品查詢直接 403，
商品頁顯示「找不到商品」。**匿名訪客不受影響**（public policy 是 `['*']`），
所以先前用匿名與管理員測都沒發現。已將這兩個 collection 改為 `['*']`。

> 教訓：**新增欄位後要檢查所有 policy 的欄位清單**，明列式權限不會自動涵蓋新欄位。

### 隱私：匯款帳號原本是公開可讀的

`site_settings` 的 public 權限是 `['*']`，因此階段 1 新增的
`bank_name` / `bank_account` / `bank_account_name` **任何人都能透過 API 讀取**。

已改為明列並排除這三個欄位。連帶地 `settingsService` 也必須拆成兩支：

- `getSettings()`——只含匿名可讀欄位。這支會在 Footer / LineButton 等未登入也會出現的
  元件被呼叫，**夾帶任何受限欄位都會讓整個請求 403，連 LINE 按鈕都會一起消失**。
- `getPaymentInfo()`——匯款資訊，只在「待付款」的訂購單明細呼叫。

## 階段 4-A：後台改為「存檔即生效」（2026-09-04）

### 拿掉手動 flow 按鈕

原本三顆按鈕（確認報價／確認收款／確認出貨）是 `location: item` 的手動 flow，
在 Directus 項目頁**右上角的 ⚡ 圖示裡**，很難發現。更麻煩的是 flow 作用於「已儲存的資料」，
老闆改完運費／折扣得**先存檔、再點閃電**，是兩段式操作，對非技術使用者太繞。

**已全部刪除**，改用 `items.update` 的 action flow：每次儲存訂購單時自動

1. 重算 `confirmed_total` ＝ Σ(確認單價 ?? 原單價) × 數量 − 折扣 + 運費（含滿額免運規則）
2. 狀態改為 `paid` / `shipped` 時補上 `paid_at` / `shipped_at`

老闆的操作變成：**改欄位 → 選狀態 → 存檔**。不需要知道 flow 存在。

> `item-update` 必須設 `emitEvents: false`，否則會再次觸發自己形成無窮迴圈。
> exec 在讀不到品項時會 throw 以中止後續步驟——客人回報匯款也會觸發本 flow，
> 那個情境下讀不到品項是正常的，不能讓它把金額算成只剩運費。

出貨必填單號改用 Directus 原生的**條件式欄位**：`tracking_number` 在
`status = shipped` 時自動變必填，沒填就存不了——比事後在 flow 裡擋更早也更好懂。

### 實測

| 操作 | 結果 |
|---|---|
| 只改狀態為待付款後存檔 | ✓ 自動算出 400 + 運費 120 = 520 |
| 改確認單價 200、折扣 50 後存檔 | ✓ 自動算出 (200×3 + 50×2) − 50 + 120 = 770 |
| 狀態改已付款 | ✓ `paid_at` 自動填入 |

> 測試時發現：用 raw API 送 `items: [...]` 整個陣列會把沒列出的品項**刪除**
> （關聯的 `one_deselect_action` 是 delete）。Directus 後台 UI 送的是
> `{create, update, delete}` 差異語法，不會有這個問題，但用 API 操作時要注意。

## 階段 4-C：新訂單通知信（2026-09-07）

### 郵件出口的選擇

原本考慮在正式站 VM 上安裝 mailcow，實測後**不採用**：

- **Hetzner 封鎖對外 port 25**（實測連 Gmail MX 全部逾時）。mailcow 裝了也無法直接投遞，
  必須再接外部 relay——而「自己送信」正是自架 mailcow 的主要價值，這條斷了就只剩維護成本。
- 資源上 mailcow 官方最低約 6GB RAM，該 VM 可用 6.7GB 且已跑著 Directus、Postgres、
  Redis、Traefik 與兩個前端 slot，沒有餘裕。
- 投遞率：全新網域 + Hetzner IP 段，需自行處理 SPF/DKIM/DMARC/PTR 並花數週養信譽。

VM 對外 **587 埠可通**，所以走 relay 沒問題。

> 順帶查到：既有的 mailcow 在另一台 Oracle 主機（`mail.jaao.tw`，服務 `jaao.tw`），
> 那台的 port 25 **同樣被封**，它是透過 Oracle Cloud Email Delivery relay 出去的。
> Hetzner 連得到 `mail.jaao.tw:587`，所以拿它當 relay 也是可行方案。

**決定：先用 Resend**，之後要換自架再換（換掉只是改 `.env` 的幾個變數）。

### 設定方式

Directus 目前**完全沒有任何 `EMAIL_*` 變數**，這就是通知信一直做不了的原因。
設定檔在 VM 的 `/root/gtsWebSite/directus/.env`：

```bash
EMAIL_FROM="金同心訂購單 <noreply@<已驗證網域>>"
EMAIL_TRANSPORT="smtp"
EMAIL_SMTP_HOST="smtp.resend.com"
EMAIL_SMTP_PORT="587"
EMAIL_SMTP_SECURE="false"      # 587 走 STARTTLS，不是一開始就加密的 465
EMAIL_SMTP_USER="resend"       # 固定字串，不是信箱
EMAIL_SMTP_PASSWORD="<Resend API key>"
```

⚠️ Resend **必須先驗證寄件網域**才能寄信；未驗證前只能用 `onboarding@resend.dev`。

### 通知信的實作

掛在既有「訂購單送出後處理」flow 的**尾端**，不另開 flow——單號是那支算出來的，
分開做會遇到「信寄出時單號還沒產生」的競態。最終步驟：

```
反查登入者的 customer → 計算單號與小計 → 寫回訂購單 → 讀取通知信箱 → 寄出通知信
```

- 寄信刻意排在**寫回之後**：實測 SMTP 未設定時寄信步驟失敗，
  但**訂單的單號、小計、客戶都正常寫入**，不影響客人送單。
- 收件人存在 `site_settings.order_notify_email`，老闆可自行修改，不必動 flow。
  該欄位已從 public 與 customer access 的可讀清單排除。
- 品項清單在 exec 裡組成純文字再帶進樣板——比在 mustache 裡迭代可靠。

### 順手修掉的 bug：後台代客人建單時客戶被覆寫

flow 原本無條件用「登入者的 customer」覆寫。但「自動建立客戶資料」那支 flow
會替**每個**使用者建 `customers` 資料列（包含老闆），所以老闆在後台代客人建單時，
客戶會被改成他自己。

改為 **payload 有帶 `customer` 就尊重它**：客戶端無權寫該欄位（送了會 403），
能出現在 payload 裡的一定是管理員／店務指定的；客戶自己送單時 payload 沒有這個欄位，
才依登入帳號反查補上。

| 情境 | 結果 |
|---|---|
| 後台指定鯊鯊建單 | ✓ 客戶維持鯊鯊 |
| 後台未指定 | ✓ 依登入者補上 |
| 客戶自己送單 | ✓ 依登入帳號補上（客戶端無法指定） |

## 階段 4-C 完成：通知信實測（2026-09-07）

以 Resend API 查證投遞結果，**狀態 `delivered`**，而非僅「log 無錯誤」。

### `EMAIL_FROM` 只能填純位址

這個 Directus 版本會把整個 `EMAIL_FROM` 字串當成信封寄件人送進 SMTP 的 `MAIL FROM`，
**只要帶顯示名稱就會 501**：

| 值 | 結果 |
|---|---|
| `金同心訂購單 <noreply@gtxin.com.tw>` | ✗ 501 Bad sender address syntax |
| `"金同心訂購單" <noreply@gtxin.com.tw>` | ✗ 501 |
| `GTS Hardware <noreply@gtxin.com.tw>`（ASCII） | ✗ 501 |
| `noreply@gtxin.com.tw` | ✓ delivered |

> 連 ASCII 也不行，所以不是編碼問題。

**顯示名稱要改 Directus 的專案名稱**，不是 `EMAIL_FROM`——Directus 用 `project_name`
當寄件者顯示名。原本是預設的 `Directus`，收件匣會顯示「Directus <noreply@…>」。
已改為 **金同心實業**，順帶讓老闆的後台介面也不再顯示預設品牌。

> 另注意 docker compose 的 `env_file` 解析器：值裡有 `<`、`>` 又只用雙引號包住時，
> 剝掉引號後會把 `<noreply@…>` 當成新的變數名而報錯。純位址沒有這個問題。

### 修掉的兩個內容錯誤

1. **客戶名稱取錯人**。原本取自 `compute2` 的 `my_customer`（登入者的 customer），
   後台代客人建單時會顯示成老闆自己。已改為在寫回後重讀訂單、取**該訂單實際的客戶**。
2. **信中的後台連結寫死舊網域**。已改為 `core.gtxin.com.tw`。

### 最終的 flow 步驟

```
反查登入者的 customer → 計算單號與小計 → 寫回訂購單
  → 讀回已寫入的訂單 → 讀取通知信箱 → 取出收件人 → 寄出通知信
```

「取出收件人」是必要的一步：`item-read` 讀單例時可能回物件也可能回陣列，
樣板語法無法分支，只能在 exec 裡正規化。少了它會得到難懂的
`No recipients defined`。該步驟在未設定通知信箱時會 throw 以中止鏈結——
訊息比 nodemailer 的原始錯誤好懂得多。

### 收件人設定

`site_settings.order_notify_email`，目前為 `jack580936@gmail.com`（測試用），
之後改成老闆的信箱即可，不必動 flow。該欄位已從 public 與 customer access 的
可讀清單排除。

### 已驗證的信件內容

主旨 `【新訂購單】GTS-260907-0036　楊佳豪`；內文含單號、客戶、聯絡方式、
參考小計（含「另有詢價品項」提示）、品項清單（詢價品標示為「（詢價）」）、
客戶備註，以及可直接開啟該訂單的後台連結。

## 階段 4-D：給客人的通知信（2026-09-07）

### 為什麼「待付款」那封是必要的，不是加分項

老闆確認金額後，客人**完全不知道該去付錢了**——要嘛自己定期回網站看，要嘛等老闆打電話。
若還是得打電話，這套系統就少做了一半的事。

這與當初做狀態追蹤是同一個問題的兩面：追蹤解決了「客人匯款後瞎等」，
這封信解決「客人匯款前瞎等」。

### 寄與不寄的取捨

| 時機 | 寄給客人 | 理由 |
|---|---|---|
| 訂單送出 | ✅ | 客人送出後信箱空空會懷疑成功了沒；單號也留在信箱 |
| → 待付款 | ✅ **必要** | 通知應付金額與匯款方式，客人才知道要行動 |
| → 已出貨 | ✅ | 附貨運單號，客人自行查件 |
| → 已付款 | ❌ | 價值有限；老闆對完帳客人很快就會收到出貨通知 |
| → 已取消 | ❌ | 沒有說明原因的取消信體驗比一通電話差，讓老闆打電話 |

這些都是**交易信**（綁定客人自己發起的特定訂單），非行銷信，
無同意書與退訂連結的法規要求。

### 最大的風險：重複寄信

更新流程是**每次存檔都會跑**的，老闆調價格可能存三次。因此狀態信只在
`$trigger.payload` 真的含有 `status` 欄位時才寄——Directus 後台只送有異動的欄位，
這個判斷夠準。**實測「只改折扣」確實沒有寄出任何信。**

另外「待付款」信在 `confirmed_total` 為 null 時會中止，避免客人收到「應付 NT$0」。

### Flow 串接

建立流程（客人確認信刻意排在老闆通知信**之前**）：

```
反查 customer → 計算單號小計 → 寫回 → 讀回訂單
  → 組客人確認信 → 寄出 → 讀通知信箱 → 取出收件人 → 寄老闆通知信
```

> 順序有意義：客人那封幾乎不會失敗（會員一律 Google 登入必有 email），
> 老闆那封在「訂單通知信箱」未設定時會 throw 中止後續。放前面才不會被牽連。
> 原本想用 resolve + reject 雙路徑徹底解耦，但 Directus 限制
> `resolve` / `reject` 的目標必須唯一，同一個 operation 不能被兩處指向。

更新流程：

```
讀訂單 → 讀品項 → 讀設定 → 計算金額 → 寫回
  → 讀回訂單 → 組客人狀態信 → 寄出
```

### 實測結果（皆以 Resend API 查證為 delivered）

| 動作 | 結果 |
|---|---|
| 建立訂單 | ✅ 客人收到「【訂購單已送出】」、老闆收到「【新訂購單】」 |
| 只改折扣 | ✅ **沒有寄出任何信** |
| 改為待付款 | ✅「【待付款】GTS-…　應付 NT$580」，含匯款資訊與備註說明 |
| 改為已付款 | ✅ 依設計未寄信 |
| 填單號並改為已出貨 | ✅「【已出貨】GTS-…」，含貨運單號 |

### 待辦

「待付款」信裡的匯款資訊取自 `site_settings`，目前為空——
上線前必須填入銀行、帳號、戶名，否則信裡會顯示「匯款資訊尚未設定，請直接與我們聯絡」。
