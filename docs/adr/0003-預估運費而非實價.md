# 前台運費是預估值,不進入應付金額

## Decision

訂購單頁顯示的運費是**預估值**,依 `site_settings` 的兩個欄位算出:

- `default_shipping_fee` — 一箱的運費
- `free_shipping_threshold` — 免運門檻

**一律以一箱計。** 實際箱數由老闆逐單看內容物決定,填入 `orders.shipping_fee`——
**那個值才進入應付金額**,前台這個數字自始至終不參與計算。

四條綁定規則(實作於 `utils/orderTotals.js` 的 `estimateShipping()`):

1. **設定不完整 → 運費列整行不渲染。** 不填寫死的預設值頂替。完整性只由
   settings store 的 `shippingRule` getter 認定,`estimateShipping()` 收的是它的
   結果(規則物件或 null),不重複判斷欄位——兩邊各判一次,規則遲早會分歧。
2. **運費或門檻 ≤ 0 一律視為未設定。** **全站免運促銷不在支援範圍**——沒有人
   要求過,做出來只是憑空多三處分支。但 0 也不能落到收費那條路:那會渲染成
   「NT$0,再買 NT$1,900 免運」,金額沒錯而加購提示在騙人。當作未設定最安全,
   失敗方向是「少顯示一行」而不是「顯示假的優惠」。真要辦促銷時再刻意實作。
3. **門檻判斷排在詢價判斷之前。** 標價部分自己就已達門檻時,再加上詢價品項只會
   更多,免運是確定的,直接顯示免運。
4. **未達門檻又有詢價品項 → 不給數字**,顯示「報價時一併確認」。說明頁的對應
   句子**必須帶「未達免運門檻」這個條件**,否則會與第 3 條互相矛盾。
5. **金額只從 Directus 讀,不寫死。** 包含 `Shipping.vue` 與 `Faq.vue` 的說明文案
   (走 `composables/useShippingCopy.js`),設定讀不到時改用不帶數字的說法。

### 為什麼不用「折扣」代替免運促銷

`orders.discount` 是**單張訂單**的欄位,老闆確認金額時填;運費規則是**全站**的,
客人**送出之前**就看得到。兩者的時機與範圍都不同:用折扣辦免運,客人在購物車
看到的仍是「運費 NT$140」,要等他送出、老闆手動減掉、他才發現有優惠——促銷
錯過了它唯一該起作用的那一刻(還在猶豫要不要買的時候),而且每張單都要記得減。
語意上也不對:折扣是「這批貨算你便宜」,不是「這次不收運費」,混用會讓應付
金額的拆解變難解釋。

## Context

老闆的實際作業是:客人送出後,他看內容物判斷幾個箱子裝得下,再填運費。運費規則本身
很簡單(新竹貨運 1 才約 120、2 才約 150,一箱長寬高總和 90–120 公分、20 公斤以內),
但**前台沒有任何資料可以推算箱數**——`product_variants` 只有
`spec_name / sku / price / stock / barcode / variant_image`,沒有重量、材積或每箱件數。

於是有兩條路:前台不講運費(客人到最後一刻才知道要付多少),或講一個可能被推翻的
預估值。選後者,並用命名與文案把「這是預估」講清楚。

第 2、3 條看似不對稱,但都服從同一個原則:**只在答案確定時才給數字。** 已達門檻時
詢價品項不會讓結果改變(金額只會更多),所以敢講;未達門檻時小計不是這張單的實際
金額(那項詢價的可能報 4000),所以不敢講。這與 `hasQuoteItems` getter 存在的理由
是同一件事——小計不完整時就不能被當成總價呈現。

第 4 條有具體痛點:在此之前,`Shipping.vue` 寫著「運費依重量、材積與配送地區計算,
將於報價時一併告知」,而運費功能**根本還沒實作**——`site_settings` 的兩個欄位被讀
進前端後就丟掉,零讀取端。文案與行為分家沒有任何機制會發現,是人去讀才發現的。
把數字綁回同一個來源,改價只要動後台,三處(訂購單頁 + 兩個說明頁)一起跟上。

## Consequences

- **客人看到的數字可能偏低。** 誤差是單向的:預估只算一箱,實際可能兩箱。發生區間
  限於「未達免運門檻卻需要分箱」——五金工具重且佔空間,這比直覺上更常見。緩解靠
  文案(「預估」「重物與大材積另行報價」「需分箱寄送時依實際箱數調整」)與老闆逐單
  調整,**不靠程式碼**。
- **運費規則改變只需動 Directus**,不必發版。但 `Shipping.vue` 裡「長寬高總和 90 公分、
  20 公斤」那句是寫死的——它描述的是貨運公司的級距而非本站定價,改的頻率不同。
  若哪天連這個也要可設定,得再加欄位。
- **老闆填的運費與前台預估不一致時,前台不會提示落差。** 明細頁顯示的是實際值,
  客人可能記得自己看過 140。目前認為不值得為此加一列說明。
- 應付金額的公式(`確認後小計 − 折扣 + 運費`)不受影響——它從來只用老闆填的值。
