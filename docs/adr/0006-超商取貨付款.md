# 超商取貨付款：交貨方式是一個選擇，不是兩個

## Decision

訂購單新增**交貨方式**（`orders.delivery_method`），兩個值：

- `cvs_cod` — 7-11 超商取貨付款
- `home_delivery` — 宅配新竹貨運 + 事後匯款（原本唯一的路）

**配送與付款綁成同一個選擇，不拆成兩個欄位。** 兩種組合是鎖死的：走交貨便
必然貨到付款，走宅配必然匯款。拆開會憑空生出兩個我們不提供的組合（超商取貨
＋匯款、宅配＋貨到付款），而每個不存在的組合都要在 UI、送出驗證、Directus、
狀態文案各擋一次。

值域為 `cvs_cod` / `home_delivery` / `pickup`（自取＝來店取、現場付現；前台目前不提供，
只在 Directus 供 Admin 選）。只有超商那個值把付款寫進名字裡，因為它是三者中唯一一個
綁定不直觀的——宅配配匯款、自取配現金是預設路徑，沒有人會搞錯，而「超商取貨但先匯款」
是真的有人會想加進來的組合。

`orders.shipping_method` **同時刪除**。它不是閒置欄位——它是一個設定完整的
select-dropdown（`home_delivery` / `pickup` / `cvs`），而且**有一筆真實資料**：
`GTS-260915-0042` 已經以 `cvs` 出貨。留著會變成一個和 `delivery_method` 長得一模一樣
的欄位，往後要改配送邏輯的人（或 agent）會有兩個候選而沒有線索。

⚠️ **刪除前必須先把那筆資料搬到 `delivery_method`**（`cvs` → `cvs_cod`）。那是訂單
本身的歷史，不能隨欄位一起消失。
⚠️ **刪欄位與移除 `orderService.js` 的 `ORDER_FIELDS` 必須同一次進版**，否則所有訂單
讀取一起炸（明細頁、列表頁、完成頁）。

### 七條綁定規則

1. **超商的運費規則與宅配完全分開，`free_shipping_threshold` 對超商不適用。**
   免運門檻是老闆對宅配運費的補貼；交貨便的運費是 7-11 直接從代收款扣走的，
   老闆想免也免不掉那筆錢。門檻若是 1,900，照套的結果是 1,900 以上的超商單
   全部免運，老闆每單自吃 65–100。

   **含詢價品項時一律不給數字**，與 ADR 0003 第 4 條同一條規則：只在答案確定時才給。
   級距查的是代收金額，詢價品項報價後會把它整個墊高（一項報 4,000 的就跳三階），
   先講的數字必然被推翻。⚠️ 這與第 4 條的 `cvsBlockReason` **刻意不同調，不要順手
   統一**：那邊問「會不會超過上限」，詢價只會更超標所以敢判；這邊問「收多少」，
   詢價讓答案未定所以不敢講。

2. **級距表寫死在程式，不進 `site_settings`。** 這是 ADR 0003 第 5 條「金額只從
   Directus 讀」的**例外**，判準是同一份 ADR 的 Consequences 已經劃好的線：
   `Shipping.vue` 裡「長寬高總和 90 公分、20 公斤」那句也是寫死的，因為
   **它描述的是貨運公司的費率而非本站定價，改的頻率不同**。老闆改不動 7-11 的
   公告費率，後台給他一個能改的欄位只會製造與 ibon 對不上的機會。

   ⚠️ **常數實作的是 L0（自己拿去門市寄）的數字，不是綠界的**，因此命名為
   `CVS_IBON`：級距 60/70/80/90/100、代收上限 5,000。理由見下面「上線第一天走哪條
   管道」——本 ADR 的 Context 選了綠界（L1），但那要等老闆申請開通，而在那之前唯一
   能走的就是自己去門市寄。名字帶管道是刻意的：**改走綠界時要換掉的是整個常數**
   （運費 65 元固定、上限 20,000），中性的名字會讓那次替換看起來像調個欄位。

3. **級距用含運的代收金額查，疊代到收斂。** 7-11 的表是依代收金額分階，而代收
   金額含運費——980 查到 60，但實際代收 1,040 已經跳進下一階，7-11 收 70。
   直接用小計查會讓前台顯示 60、老闆建單打 70，而客人是在櫃台當場發現的。
   **迴圈最多跑兩圈**：加運費只會讓金額變大、階只會往上跳，而階寬 1,000 遠大於
   最高運費 100，不可能連跳兩階。

4. **前台只擋確定的：`小計 + 運費` 超過代收上限時超商不可選。** 這是 ADR 0003
   第 3 條的鏡像——答案確定時才敢下判斷。尺寸與重量完全交給老闆逐單看。
   ⚠️ **比的是含運的代收金額，不是小計。** 上限管的是店員實際收的那個數字，而運費
   是它的一部分：小計 5,000 看似剛好達標，代收其實是 5,100，會等到老闆建單時才被
   7-11 擋下來——那時包裹已經包好了。
   詢價品項刻意不納入判斷（本 ADR 初版寫成「且無詢價品項」，那是錯的）：它們只會讓
   代收金額更多，不可能把超標的單拉回上限以內，多一個條件只是讓判斷漏掉真的超標的單。

5. **`product_variants.can_ship_cvs` 預設 `false`，訂購單裡任一品項未勾就不給選超商。**
   ⚠️ **停用的文案不可以把原因寫死成「尺寸」**：這個旗標是判斷不是量測，而且不能寄
   的理由未必是尺寸——耗材與化工整批設 `false` 是因為**超商禁寄危險物品**，那是另一
   條規則。講死一個理由會在那一類商品上直接說錯話。
   老闆憑經驗勾，**不必拿尺量**——量了也沒用，檢查點在超商櫃台，店員當場量。
   預設 `false` 是刻意的：失敗方向是「少一個選項」而不是「客人選了寄不出去」，
   與 ADR 0003 第 2 條同一個原則。代價是上線當下所有品項都不能走超商。

6. **超商單走 `pending → quoted → shipped`，`paid` 永不出現。** 錢要等客人取貨、
   再等隔週撥款，出貨當下根本還沒到帳；硬推 `paid` 會讓客人在「已出貨」之後
   才看到「已付款」，順序是倒的。不新增狀態鍵（`CONTEXT.md` 明令不發明中間
   狀態），只讓 UI 文案依交貨方式分岔。`payment_note` 那整塊 UI 對超商單隱藏
   ——ADR 0004 的對帳規則對它是空的。
   Directus 的下拉 label 是全站一份、無法分岔，因此 `quoted` 改標「已確認」：
   那本來就是這個鍵的老闆視角（已報價），「待付款」是借了客人的視角放進後台。

7. **超商單才驗手機格式（`09` 開頭 10 碼）。** `OrderForm.vue` 對電話「只驗非空
   不驗格式」的理由是「擋掉真客人的代價高於擋掉爛資料」——**這個比較在超商單上
   反過來**：7-11 到店只發簡訊，市話收不到，收不到就是棄件，而棄件的運費老闆
   自己吃。手機在這裡是物流的硬需求，不是偏好。
   ⚠️ 兩條分支不一致是刻意的，不要順手統一。

## Context

起因是一張小額訂單：走宅配的運費比商品還貴，老闆想直接寄超商。

**而那張單已經寄出去了。** `GTS-260915-0042` 由老闆在 Directus 手動標成 `cvs`、填上
物流單號寄出，全程沒有經過前台。所以這個 ADR 記的不是「要不要做這件事」——事情已經
在做了，只是客人無從選擇、系統無從得知。要補的是讓它從一次性的人工操作變成可重複的
流程。

### 為什麼不串物流 API（L2）

三個層級：**L0** 老闆去 ibon 自己建單；**L1** 在物流商後台網頁建單、印貼紙、
拿去門市交寄；**L2** API 串接（電子地圖 + 建單 + 貨態 webhook）。

選 **L1**。老闆在蝦皮**已經是這個流程**（印貼紙、包裝、拿去門市），不必學新東西。

L2 被否決的理由不是難，是**不划算**：它唯一解掉的是「客人選門市」這一個小問題，
但要換來簽約開通（`eshopid` / `MerID`）、Worker 新增一條收 POST callback 的 route、
HashKey/HashIV 的保管、貨態 webhook，以及 `CONTEXT.md` 那句「沒有物流串接」整條
作廢。而且**串了也擋不掉尺寸問題**——建單 API 根本沒有材積欄位，7-11 是在櫃台
才量的。取貨門市因此收成自由文字，旁邊放 7-11 官方門市查詢的外連（純導流）。

### 為什麼不叫客人去蝦皮買

外部通路（`CONTEXT.md` 的 External channel）本來就存在，小額單導去蝦皮是零實作
的選項。否決的理由是算術：

|  | 蝦皮 | 自己走 L1 |
|---|---|---|
| 成交一筆 1,500 的單 | 抽 200–255（2026 新制合計常到 13–17%） | 81（運費 65 + 代收 0.75% + 稅） |
| 客人棄件 | **平台吸收**，成交手續費不收 | **去程運費 65–100 照收** |

損益平衡點在**棄件率 67%**，實務是 5–15%，差得非常遠。蝦皮那 15% 買的是流量，
而在這個情境裡客人已經在站上填完訂購單了，流量價值是零。

⚠️ 但要知道：老闆覺得「蝦皮棄件還好」，是因為**那筆錢一直是蝦皮在付**。搬到自己
的站上，同樣的棄件率會第一次真的扣到他。

### 為什麼物流商選綠界而不是 PayUni

三家（綠界／藍新／PayUni）的 C2C 超商物流費率幾乎相同（運費 65、代收 0.75%），
所以不該用費率選。選綠界是因為四大超商全支援（客人家附近不一定是 7-11）、文件
最完整、L1 後台建單最成熟。

PayUni 唯一的優勢是信用卡 2.4%——**對一個不收線上款的站等於零**，而它的缺點
（撥款 T+7 再加 1–3 個工作日）是實的。

發票維持 Amego（光貿），**不換**。它是純發票加值中心，不做金流物流，因此對物流
商的選擇沒有任何約束；作廢與折讓是法定功能，三家加值中心都支援，不構成選擇理由。

## Consequences

- **有一半的改動不在這個 repo。** Directus 那端要：新增兩個 `orders` 欄位與
  `product_variants.can_ship_cvs`、刪 `shipping_method`、開客戶端寫入權限、改 status
  label，以及信件文案分岔。前端綠燈不代表這條路通。
  除了刪 `shipping_method` 之外，都已於 2026-09-16 完成。

- **信件其實只有兩支腳本，不是三個 flow**（本 ADR 初版寫成「三個 flow」，那是錯的）。
  兩個 orders flow 各有一支 `exec` 負責組信，`mail` 操作只是把結果送出去：

  | Flow | 組信的 operation | 涵蓋 |
  |---|---|---|
  | 訂購單送出後處理（`items.create`） | `ack_build` | 送出確認信 |
  | 訂購單存檔後自動計算（`items.update`） | `cust_build` | `quoted` 與 `shipped` 兩封 |

  所以分岔全部收在這兩支腳本的 `order.delivery_method === 'cvs_cod'` 判斷裡。
  `paid` 本來就在 `cust_build` 的狀態白名單之外，超商單不會觸發，不必另外處理。

- ⚠️ **`ack_build` 拋錯會讓老闆收不到新單通知。** 送出流程的鏈是
  `… → ack_build → ack_mail → notify_to → pick_to → notify_mail`，客人那封排在老闆那封
  **之前**。`ack_build` 任何一個 `throw`（讀不到訂單、客戶沒有 email）都會讓整條鏈停在
  那裡，於是老闆的通知信也不會寄——而 `docs/adr/0004` 已經確立那封是**老闆唯一的觸發器**，
  沒收到就等於這張單沒人看。改這支腳本時務必讓它不要新增拋錯路徑。

- **`shipping_method` 的刪除是部署順序的一部分，不是收尾的雜項。** 線上前端的
  `ORDER_FIELDS` 還在要這個欄位，而 Directus 對不存在的欄位回 403，所以先刪就是
  **線上所有訂單讀取立刻全掛**。順序只有一種：前端改完並部署 → 才刪欄位。

- **出貨通知信必須帶門市、應付金額、7 天期限三件事。** 那是客人唯一一次在掏錢前
  讀到金額的機會，而 7 天期限是**唯一一個能壓低棄件率的零成本槓桿**。

- **棄件的代價是老闆的時間，不是帳上的數字。** 金錢面只有一趟去程運費 65–100
  （退回運費目前由 7-11 吸收，是推廣期優惠，會變）。真正的負擔是跑一趟原寄件
  門市取回、商品被綁兩週、以及發票要處理。

- **月底出貨的超商單風險比月初高。** 營業稅雙月一期，棄件退回的兩三週很容易跨期，
  一跨期就從「作廢」掉進「折讓」，而折讓要買方確認、B2C 還有開立翌日起 2 日內
  上傳的時限。這是老闆的作業知識，程式不處理。

- **一張單需要多箱時，超商這條路沒有解，而且刻意不做。** 宅配早有解（ADR 0003）：
  前台一律以一箱估，實際箱數老闆逐單判斷後填 `orders.shipping_fee`，新竹貨運多箱是
  同一筆託運、一個單號，`tracking_number` 單欄位夠用。

  交貨便不一樣，它是**按件**的——三箱就是三張獨立寄件單、三個取件編號、三筆各自的
  代收金額。結構上撞到三件事：`orders.tracking_number` 是單一字串欄位塞不下三個；
  5,000 上限是**每件**算的，拆箱後怎麼分攤沒有定義；客人要去櫃台付三次。

  **但這個情境幾乎到不了**：最長邊 45cm、10 公斤、代收 5,000 三條線，會在「需要第二
  箱」之前就先把單擋掉。塞得進 45cm 又不到 5,000 元的東西，通常一箱就夠。真遇到了
  就改宅配，或請客人拆成兩張單——與 ADR 0003 第 2 條同一個判斷：沒人要求過的分支，
  做出來只是憑空多三處。

- ⚠️ **`OrderDone.vue`（送出完成頁）是這次差點漏掉的檔案。** 它原本寫死「確認後會
  通知您應付金額與**匯款方式**」——對超商單是錯的指示，那個匯款資訊永遠不會來。

  **codex 與 `/code-review` 兩軸都沒抓到，因為那支檔案不在 diff 裡——而那正是 bug。**
  基於 diff 的審查結構上看不見「該改而沒改的檔案」，只有真的把單送出去才會撞到。
  修法是讓交貨方式隨 router state 帶到完成頁，並保留**交貨方式不明時的中性文案**
  （重新整理會讓 history state 消失，那時寧可少講一句，也不要講一句對一半客人是錯的）。

- **上線前要先批次勾 `can_ship_cvs`**，否則功能等於沒開。

- **老闆在 Directus 要記得超商單別按「已付款」。** 那是人的紀律，程式擋不住。

- **上線第一天走的是 L0，不是 Context 裡選的綠界。** 綠界要申請開通，那件事在 repo
  之外、也還沒發生；在那之前老闆唯一能做的就是自己拿包裹去 7-11 門市寄。所以程式
  實作的是 `CVS_IBON`（級距 60–100、代收上限 5,000），而 Context 記的是**目標**管道。

  這個落差有代價，要明講：**5,000–20,000 的單現在會被拒絕走超商**，而走綠界的話
  它們是可以的。等綠界開通後要換的是：`CVS_IBON` 整組換成綠界的（65 元固定、上限
  20,000）、`Shipping.vue` 與 `useShippingCopy` 會自動跟上（數字都從常數讀），
  以及本 ADR 這一段。程式裡沒有第二處寫死這些數字。

  「兩者本來就是不同管道」這件事最初沒被寫進來，是 `/code-review` 的 spec 軸抓到的
  ——Context 寫綠界、程式寫 ibon，而兩份文件各自都自洽，所以不並排讀就看不出來。
