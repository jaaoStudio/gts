# `payment_note` 是對帳線索，不是付款證據

## Decision

**錢有沒有到帳，唯一的真相來源是銀行明細。** 客人回報的匯款末五碼
（`orders.payment_note`）只是加速「這筆入帳對應哪張單」的比對，不構成付款證據。

四條綁定規則：

1. **客人的回報不推進狀態。** `customer access` 的 update 只開放 `payment_note`
   一個欄位，且限 `status = quoted`；`paid` 一律由老闆確認入帳後自己推進。
   （這是原始設計就有的，此 ADR 只是把理由寫清楚。）

2. **驅動老闆去對帳的是銀行通知，不是客人的回報。**
   因此**刻意不做**「客人回報後寄信給老闆」那封信——銀行已經會通知，那封信不增加
   資訊，而且只在客人配合時才發，當驅動器會讓沒填的單沒人去看。
   （「新單成立」那封不同：客人送單沒有任何外部觸發器，那封是必要的，
   已實作於 `訂購單送出後處理` flow 的 `notify_mail`。）

3. **老闆拿到入帳後，依 `payment_note` 的三種狀態處理：**

   | `payment_note` | 處理 |
   |---|---|
   | 空的 | **不要填。** 空著代表「客人沒照流程走，我們自己對出來的」，是有意義的資訊 |
   | 有值且與銀行相符 | 直接確認收款 |
   | 有值但不符 | 打電話確認（多為打錯字或用別的戶頭），**然後修正成銀行上的數字** |

4. **不新增「內部備註」欄位。** 事後查帳的依據是：銀行明細（金額／日期／匯款人）
   ＋ `confirmed_total` ＋ `paid_at`（狀態改成已付款時自動填）＋ Directus revisions
   （誰改的、原值是什麼）。四者都不依賴 `payment_note` 正確。

## Context

第一版收款維持匯款、不串金流（理由見 `docs/proposals/訂購單.md` 的「收款」章節：
匯款 0% 手續費 vs 金流約 2.8%）。代價是人工對帳，於是產生一個問題：
**老闆怎麼知道客人匯款了，以及怎麼知道那筆錢對應哪張單。**

原本的直覺是「客人回報後寄信通知老闆」，但那會把一個**只在客人配合時才發生**的
事件當成驅動器——沒填的單就不會有人去看。而銀行通知本來就存在、且不依賴客人。

### 考慮過但否決的做法

- **保留 `payment_note` 的 `readonly: true`**（原始設定）。
  否決：規則 3 的「填錯時修正」在唯讀下做不到，那條規則會變成一份**看起來完備、
  實際無法執行**的作業約定。保留唯讀的代價落在**每一次對帳**（不符的值永遠留著，
  每次打開都要重新判斷是打錯還是配對錯），關掉的代價只落在「有人惡意改」——
  而 `店務` 目前只有老闆一個使用者，且 revisions 保留每次變更的完整快照。
  → **2026-09-10 關掉 `meta.readonly`。**

- **新增 `internal_note` 欄位**讓老闆記下「我對到的是哪一筆入帳」。
  否決：上面第 4 條的四個來源已足以事後追溯，多一個欄位就多一個要維護、
  且會與 `payment_note` 的定位混淆。

- **客人回報後寄信給老闆**。否決，理由見 Decision 第 2 條。
  （這是**便利性**而非可靠性問題——訂單量起來、老闆覺得搜尋很煩時再加是合理的。）

- **老闆幫沒填的客人補上末五碼**。否決：補了不增加「錢到了」的資訊，卻會讓這個
  欄位從「客人自己說的」變成「某個人打的字」，之後沒人能判斷值是誰寫的。
  混來源的欄位就是沒人能信的欄位。

## Consequences

- `payment_note` 的 provenance 移到 Directus revisions：當前值反映現實，
  「客人原本填 54321、老闆改成 12345」的歷史查得回來，但當前值上看不出被改過。
- Directus 後台的 `payment_note` 欄位已加上說明（空白是正常的、不符時請確認後修正），
  老闆看到的是有上下文的欄位而不是一個裸欄位。
- `orders` 其餘九個唯讀欄位都是「Flow 會覆蓋你所以不准手改」，`payment_note`
  不屬於那一類——它混在唯讀清單裡本來就是不一致的，關掉之後分類反而更清楚。
- **這整套會在串接金流後被淘汰**（金流給權威的付款回調與交易序號），所以上面三條
  規則刻意是「不寫程式」就能執行的作業約定，不值得為它增加任何機制。
